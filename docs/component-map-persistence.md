# Component-map persistence

A map belongs to one owner and one overview scan. Its ID is the overview lookup ID. The overview photo ID is immutable: each component's optional box names that exact source photo. Component UUIDs and link UUIDs survive renaming, review and reopening. The map supports up to 100 components independently of segmentation masks; each linked scan group still contains one to four original photo IDs.

`needs_view`, `inspected` and `not_visible` are explicit human review states. AI output and a successful scan save do not mark a component inspected. Reviewed states carry a human review timestamp. Notes and links remain separate from AI conclusions.

## Occurrences and version compatibility

Newly seeded maps use document version 2. Distinct same-named scene suggestions remain separate components with independent UUIDs, including suggestions without a usable outline. An ambiguous scene suggestion is retained unboxed instead of being merged into a boxed component by name alone. An unambiguous primary suggestion may refer to the same primary component. These are suggested occurrences, not a verified count of physical parts: duplicates can remain and require human review. Textual locations do not create measured geometry, and all seeded components remain `needs_view` without a human review timestamp.

A version-2 component may have `suggestedLocation: { source: "ai_scene", text: "upper left" }`. This object has exactly those two keys. The source is fixed, and text is nonempty after trimming and limited to **240 Unicode code points** without truncation. The client trims accepted text; the database requires already-trimmed canonical text using the same ECMAScript whitespace set. Suggested location text remains distinct from editable human notes and a manually corrected region. It does not establish an exact location, verified contour, inspection, diagnosis or safe condition.

Version 1 remains readable and editable without suggestion metadata. Its new validator rejects any `suggestedLocation` property instead of silently dropping it; malformed version-2 metadata rejects the complete map as well. Existing maps are not automatically reseeded, rewritten, upgraded or supplemented from a later AI result. Their component IDs, human review, notes, geometry and links are retained. Explicitly choosing a reviewed legacy cloud document during conflict resolution may restore version 1 locally; local versions are not a globally monotonic sequence.

Older clients reject version-2 documents. Their device-map read raises an invalid-map error rather than returning a missing map, and the map UI exposes a loading retry rather than creating a replacement. The cloud trigger also rejects a stored version-2 map being updated to version 1. Do not downgrade or strip metadata to make an old client accept a map; retain the saved version and use a compatible client.

## Device record and concurrency

`src/services/componentMapStore.ts` keeps the canonical map in owner-scoped IndexedDB records. The map is not duplicated as mutable JSON in `Lookup` or localStorage. Its record contains the document, local revision, last observed cloud revision, last synchronized local revision, and optional sync-attempt/conflict metadata.

Edits compare the exact local revision inside an IndexedDB read/write transaction. Another tab's committed edit causes a visible stale-revision error; the stale document never silently wins. A sync acknowledgement rereads the record transactionally, checks its attempt ID and observed cloud revision, and preserves any newer device edits. Only the sent local revision is acknowledged. Account generation checks prevent delayed work from updating a newly selected account.

## Cloud contract

`public.component_maps` has primary key `(user_id, map_id)`, a JSON document, and an independent optimistic revision. SELECT, INSERT, UPDATE and DELETE are owner-only. Shop access to an underlying scan does not grant access to its map or make that scan another user's owned overview. The security-invoker trigger fixes `search_path`, validates the complete document, enforces immutable identity/original photo and next revisions, and verifies that linked scan/photo IDs belong to the same owner.

Without a confirmed cloud revision the client uses INSERT only. Otherwise it updates with owner, map ID and observed revision predicates, setting the next revision. It never uses an unconditional UPSERT. A revision conflict stores the fetched cloud document alongside the unchanged device document and advances the local revision so an older conflict screen cannot resolve a newer conflict unseen. No timestamps choose a winner.

`loadComponentMapFromCloud` imports only when no local map exists, including a second check inside the transaction. `syncComponentMapToCloud` checks each referenced original photo group's IDs through the normal authorized scan path; a missing cloud scan is uploaded before its map, when its complete evidence is available locally. Missing scans/photos, storage failures and missing migrations block map sync with an explicit message. They do not remove components or links.

`resolveComponentMapCloudConflict` requires the exact displayed local revision and an explicit device/cloud choice. Keeping the device version adopts only the reviewed cloud revision as the next compare-and-swap base. Choosing the cloud version imports the reviewed document. Neither choice automatically writes to the cloud. The UI retains a restorable device draft when the user chooses the cloud version.

Cloud map requests have a 20-second abort/response deadline. Authentication-client/session reads and referenced cloud-photo reads also have a 20-second response deadline; late read results are ignored and cannot start a map write. A two-minute durable attempt claim prevents concurrent tab saves during a normal request; after a crash it may be retried. An expired or late request still cannot overwrite a newer cloud revision, and its acknowledgement cannot clear another attempt. A lost acknowledgement is reported as uncertain, not success; retrying may expose a conflict for explicit review.

The overview foreign key uses RESTRICT: deleting the cloud overview while its map exists fails and preserves the accumulated map. Remove or export/reconcile the map before deleting that overview through an authorized administrative workflow; this slice does not add a map-delete UI. Deleting a detail scan leaves the map link intact and visibly unavailable. Another map save cannot claim that missing evidence was synchronized.

## Capture linking

The persisted photo draft includes its map ID, component ID, link-attempt UUID and preallocated lookup ID. Capture resume uses that saved target, never the currently selected component. The device lookup save and map-link transaction use separate storage systems: they are not presented as one atomic write. The matching draft must remain until the idempotent link is committed, allowing recovery by the preallocated lookup ID after an interruption. Replacing or retiring a draft compares both photo evidence and target, preventing a different draft from being retargeted or erased.

## Remaining source-binding limitation

Map references currently bind lookup and photo IDs, not a saved source-image fingerprint. The device map revision check does not verify that the overview lookup still exists or still contains the same pixels at save time. A same-ID source replacement can therefore leave an earlier rectangle attached to different image content, and an open map-area editor is not cancelled solely by that source change. Cloud reference checks and report export also do not prove that current bytes match the source used when the map was created. The cloud overview foreign key prevents deleting that cloud row while its map exists; the device store has no equivalent source-deletion guard. This occurrence-preservation change does not implement source fingerprints, source-aware save/editor checks, or a map-to-isolation correction workflow. Those require a separate slice; retained map notes and statuses are not proof of current image identity or coverage.

Occurrence extension: `20261105211101_component_map_occurrences.sql`, also generated with the installed CLI's local-only `migration new` command, is **unapplied**. It replaces the existing validation function to accept versions 1 and 2 and validate optional version-2 location metadata. It adds no columns, changes no existing rows, grants, policies, foreign keys or trigger registration, and retains the previous ownership, identity, revision, review-time, geometry and linked-photo checks. Version-2 cloud writes require this extension after the original map migration. A client rollback must preserve version-2 records; do not strip their metadata or restore the old validation function while version-2 writes remain possible. No hosted migration, deployment or credential change is authorized by this document.

Disposable PGlite verification covers owner isolation despite shared scan visibility, malformed documents, IDs/geometry, independent revisions, stale writes, overview deletion protection and retained unavailable detail links.
