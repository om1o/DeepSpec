# Vehicle references: NHTSA identity lookup

This first slice adds explicit VIN lookup and review of manufacturer-reported identity. NHTSA describes vPIC as data submitted by manufacturers, intended for model years 1981 onward. Decoding does not establish the currently installed engine, modifications, component fitment, condition, or a safe repair procedure. [NHTSA vPIC background](https://vpic.nhtsa.dot.gov/About)

The implemented flow is:

1. Open **NHTSA VIN reference** in the vehicle editor. Opening the panel reads local history; only **Look up VIN with NHTSA** starts a network lookup. DeepSpec requires a complete 17-character VIN and accepts an optional model year from 1981 through 2099. It does not infer an omitted year.
2. The signed-in client sends a JSON `POST /api/vehicle-reference` containing only `vin` and optional `modelYear`. After session and rate-limit checks, the server sends one form POST to the fixed `https://vpic.nhtsa.dot.gov/api/vehicles/DecodeVINValuesBatch/` endpoint, with `format=json` and a single VIN/year pair. Photos, symptoms, notes, jobs and customer data are not included. The upstream request omits credentials, rejects redirects and has no automatic retry or response cache. VIN is in the request body, not the destination URL. The official API documents the batch format and optional year; DeepSpec deliberately uses one full VIN per action. [NHTSA API documentation](https://vpic.nhtsa.dot.gov/api/)
3. The adapter checks that exactly one returned record matches the requested VIN. It retains the source URL, retrieval time, query, allowlisted identity facts, decode codes and both original error-text fields when present. Missing facts remain absent; engine manufacturer, cylinders, displacement and fuel type remain separate attributes rather than being combined into an invented engine code. Decode warnings remain visible. Field-use buttons are available only when the returned code list is exactly `['0']`; other responses remain viewable for manual checking. NHTSA's variable definitions say a supplied model year can be returned even if the VIN-derived year differs, so the review panel explicitly explains that it is not independent year verification. [NHTSA variable definitions](https://vpic.nhtsa.dot.gov/api/vehicles/GetVehicleVariableList?format=json)
4. The reference must be acknowledged as saved on the device before field use is enabled. Current and decoded year, make, model and engine model appear together, with conflicts and existing confirmation state visible. Each **Use decoded …** action changes only that editor field through `updateVehicleContextField`, clearing its confirmation. It does not create a human confirmation. The existing form Save action is still required.

`src/services/vehicleReferenceStore.ts` keeps immutable snapshots in IndexedDB v7's `vehicle-references` store, keyed by account and canonical VIN. History is newest first, limited to **20 references per VIN and 128 KiB per bucket**; each validated reference is at most 20 KiB. Exact retries add nothing. Changed content under the same UUID is rejected. Concurrent appends merge inside a fresh transaction. Corrupt history, account changes, quota failures and timeouts report errors without silently replacing or evicting older entries. An unsuccessful save leaves the returned reference available in the open panel for retry or explicit discard; it is not a durable recovery draft.

Reference snapshots are separate from the account-local vehicle profile. In Scanner, saving edited car details changes the profile used for future captures. Existing scans and unfinished photo drafts retain their frozen vehicle context. Selecting an older reference changes no fields until a field-use action is chosen; it does not prove that the current vehicle details were confirmed. Account/VIN changes and intervening editor changes prevent delayed results from being silently applied.

There is **no cloud synchronization or inspection-report propagation of reference snapshots/provenance** in this slice. User-applied car fields can subsequently follow the existing vehicle-context capture flow. There is no OEM manual registry, repair-diagram or service-specification integration, and no licensed OEM access has been established. Roadmap item 8 remains incomplete beyond this identity-reference slice.

NHTSA's FAQ describes public API use as free and without application registration. Its API documentation also states that automated traffic controls apply; this integration makes no throughput or availability guarantee. NHTSA permits distribution of its public information while disclaiming accuracy/completeness guarantees and endorsement. Those terms do not establish access to third-party OEM repair libraries. [NHTSA API FAQ](https://vpic.nhtsa.dot.gov/api/Home/Index/FAQ), [NHTSA terms](https://www.nhtsa.gov/about-nhtsa/terms-use)

Implementation entry points are `VehicleReferenceReview.tsx`, the shared vehicle-reference types/normalizers, `src/services/vehicleReference.ts`, `src/services/vehicleReferenceStore.ts`, `server/vehicleReference.shared.ts`, and `api/vehicle-reference.ts`. The checked-in `vercel.json` lists seven API functions and sets automatic deployment to `false` for `codex/car-vehicle-references-20261105`; this is source configuration, not a hosted deployment claim.

On November 5, 2026, the actual adapter made one live POST using a public placeholder VIN from NHTSA's own documentation. It returned Chevrolet HHR identity fields and the check-digit warning code `1`; the adapter retained that warning instead of treating HTTP 200 as a clean decode. This establishes one adapter interoperability case, not hosted DeepSpec acceptance, identity verification of a user's vehicle or general API availability. No user VIN or private vehicle data was sent. [NHTSA public POST examples](https://vpic.nhtsa.dot.gov/api/Home/Index/LanguageExamples)

Full validation status is tracked separately in the external acceptance receipt. Authored tests cover request allowlisting, warning gates, account/editor races, explicit field review, immutable storage/caps and additive IndexedDB upgrade. Native-device, authenticated hosted and real-user acceptance remain separate requirements.
